# Диздок: `@virentia/core/utils`

Сабпас со стандартной библиотекой операторов над юнитами: время (debounce/throttle/delay/interval), событийная алгебра (once/previous/reset), статус эффектов (status). Ревизия [effector/patronum](https://github.com/effector/patronum) с честным отсевом того, что в virentia закрывается `computed` и императивными реакциями.

---

## 1. Задача и критерий отбора

Patronum существует из-за двух свойств effector, которых у virentia нет.

**Нет авто-трекаемых выражений**: чтобы сказать `a && b`, нужен оператор (`and`), чтобы взять срез — `reshape`, чтобы сравнить — `equals`. В virentia всё это — однострочник на `computed`.

**Логика живёт только в связях графа**: реакция на событие в effector — это `sample`/`split`/`condition`, поэтому любое ветвление и любая хореография требуют декларативного оператора. В virentia **реакции императивные**: тело `reaction({ on, run })` — обычный код, где ветвление это `if/else`, «первый матч» и «остаток» получаются по построению, а производные события объявляются и вызываются из тела как функции. Декларативная маршрутизация операторами (`split`, `condition`, `combineEvents`) — effector-необходимость, а не наша.

Критерий включения в `utils` — оператору нужно то, чего нет ни у `computed`, ни у тела реакции:

1. **Время.** `computed` — чистая функция от значений; debounce/throttle/interval — это таймеры, состояние на скоуп и правильное умирание. В ядре времени нет вообще.
2. **Состояние между срабатываниями с правильным домом.** `once`, `previous` помнят прошлое, и это прошлое обязано жить в сторе per-scope — рукописная версия с переменной замыкания протекает между скоупами.
3. **Запись, требующая непубличного.** `reset` — единственный, кому нужно то, чего у тела реакции нет: начальные значения сторов.
4. **Диагностика эффектов.** `status` — машина состояний, которую каждый проект пишет сам и чуть по-разному.

Всё остальное из patronum — не порт, а рецепт в документации (§3).

Отдельная причина иметь пакет с теми же именами: `@virentia/effector` — мост для мигрирующих с effector, и люди, знающие patronum, должны находить `debounce`/`throttle`/`once` по привычным именам, а не переизобретать их поверх `reaction`.

## 2. Опора в ядре

- `computed` — авто-трекинг, лениво, per-scope ([store.ts](../../packages/core/lib/units/store.ts)). Закрывает всю булеву/проекционную часть patronum без единого оператора.
- `store.subscribe(fn)` зовёт подписчика как `(value, scope)` — одна подписка на стор, знающая скоуп записи. На этом стоят Store-варианты временных операторов (§4.2), тем же приёмом, что индексы в [dynamic-models §7.2](./dynamic-models.md).
- `event().map/.filter/.filterMap` — одноветочная маршрутизация уже в ядре; многоветочная — `if/else` в теле реакции с вызовом объявленных событий, оператор не нужен (§1).
- `effect` уже несёт пер-эффектные `pending`, `inFlight`, `started/done/failed/doneData/failData/settled`, `abort/aborted` ([effect.ts](../../packages/core/lib/units/effect.ts)) — patronum-операторы `pending`/`inFlight` в virentia не нужны вовсе (агрегация по нескольким эффектам — computed-однострочник над `fx.inFlight`), выживает только `status` (§6).
- `owner`/`onCleanup` ([owner.ts](../../packages/core/lib/graph/owner.ts)) — каскадный dispose; всё, что заводит таймер или подписку, регистрирует очистку и умирает с владельцем.
- `dependency()` — не-состояние per-scope, не сериализуется: там живут хендлы таймеров и аккумуляторы, которым нечего делать в SSR-снапшоте.
- `runDetached` + контракт ошибок ([run.ts](../../packages/core/lib/kernel/run.ts), [report.ts](../../packages/core/lib/kernel/report.ts)): отложенный хвост — новый корневой запуск; падение реакции ниже по течению репортится через funnel и не роняет процесс. Это то, что делает операторы времени вообще возможными без собственной обработки ошибок (§4.3).

**Ядру добавляется одно:** доступ к начальному значению стора для `reset` — `initialValueOf(store)` из `@virentia/core/internal` (значение и так лежит в замыкании `createStore`, наружу нужен только санкционированный читатель) плюс предикат `hasInitialValue(store)` — у computed сохранённого initial нет, и деградировать надо по проверке, а не по catch.

## 3. Ревизия patronum: все 29 операторов

| patronum | вердикт | почему |
|---|---|---|
| `and`, `or`, `not`, `xor`, `empty`, `equals`, `every`, `some` | не порт | `computed(() => a.value && b.value)` и т.п. — короче вызова оператора |
| `either` | не порт | `computed(() => cond.value ? a.value : b.value)` |
| `format` | не порт | `` computed(() => `${name.value} (${age.value})`) `` |
| `reshape` | не порт | несколько `computed` или `store.map` |
| `readonly` | не порт | типы уже разделяют `StoreWritable`/`Store`; рантайм-барьер — `$w.map((v) => v)` |
| `snapshot` | рецепт | `reaction({ on: clock, run: () => { $snap.value = $src.value } })` — две строки |
| `time` | рецепт | `interval` + запись `Date.now()` в стор |
| `condition` | не порт | `event.filter`/`filterMap`; многоветочно — `if/else` в теле реакции |
| `split-map` | не порт | реакция: `if/else` + императивные вызовы объявленных событий; первый матч и остаток — по построению |
| `combine-events` | не порт | состояние «рукопожатия» — сторы + `computed`; хореография именно событий — реакция с аккумулятором-стором |
| `spread` | не порт | реакция: `if ("k" in d) $k.value = d.k` по ключам; транзакцию тело реакции даёт само |
| `once` | **порт** | §5.1 |
| `previous` | **порт** | §5.2 |
| `reset` | **порт** | §5.3, единственный требует `initialValueOf` |
| `debounce`, `throttle`, `delay`, `interval` | **порт** | §4, ядро пакета |
| `status` | **порт** | §6 |
| `pending`, `in-flight` | не порт | пер-эффектные уже в ядре; агрегация — `computed(() => a.inFlight.value + b.inFlight.value > 0)` |
| `debug` | не порт | `reaction({ on: unit, run: (v) => console.log(v) })` — однострочник; живой трейсинг — работа инспектора |

Итого 8 операторов; остальное — раздел рецептов в доках, чтобы мигрирующие с patronum находили ответ по имени, которое ищут.

## 4. Время: `debounce`, `throttle`, `delay`, `interval`

### 4.1 Сигнатуры

Первый аргумент — источник, второй — миллисекунды или опции:

```ts
const search = event<string>();
const debounced = debounce(search, 300);            // Event<string>
const throttled = throttle(scrolled, 100, { leading: true });
const later     = delay(saved, 2000);

const { tick, active } = interval({ ms: 1000, start, stop });
// tick: Event<void>, active: Store<boolean> — per-scope
```

### 4.2 Оператор сохраняет породу источника

То, чего в patronum нет и что естественно в мире `.value`: операторы времени принимают **Event или Store** и возвращают ту же породу.

```ts
const $query = store("");
const $settled = debounce($query, 300);   // Store<string>: последнее устоявшееся значение
const $view = computed(() => filter(list.value, $settled.value));
```

Store-вариант — главный сценарий (поисковая строка, слайдер, скролл-позиция): дальше по графу он ведёт себя как обычный стор — `computed` от него, реакции на него, никакой пары «событие + ручной стор» не нужно.

Механика Store-варианта — ровно приём индексов: одна подписка `source.subscribe((value, scope) => …)`, таймер на скоуп записи, по истечении — запись в производный стор **в том же скоупе**. Никакого глобального таймера, который сливал бы записи разных скоупов.

### 4.3 Скоуп, умирание, контракт ошибок

- **Таймер per-scope.** Запись в скоупе A дебаунсится независимо от записи в скоупе B — иначе SSR-запрос и клиентский скоуп душили бы друг друга.
- **Хендлы таймеров живут в per-scope картах вне скоупа** (та же природа, что у `dependency()`: не-состояние) — SSR-снапшот чистый, сериализовать нечего. Сам `dependency()` не используется: это DI-примитив с обязательной провизией, а таймеры — внутренняя механика оператора.
- **Умирание.** Оператор создаётся в owner-контексте и регистрирует `onCleanup`: dispose владельца чистит таймеры во всех скоупах, событие после dispose не стреляет. Глобально созданный оператор живёт вечно — как любой глобальный юнит.
- **`await` источника не включает отложенный хвост.** `await scoped(s, () => search("x"))` завершается, когда дренаж исходного запуска осел; срабатывание `debounced` через 300 мс — **новый корневой запуск** через `runDetached`: падение реакции в хвосте репортится через funnel (см. контракт в [report.ts](../../packages/core/lib/kernel/report.ts)) и не превращается ни в unhandled rejection, ни в отказ давно завершённого `await`. Это прямое следствие пункта 5 контракта ошибок, а не особый случай.
- **`scoped` не ждёт таймеры.** Иначе любой `interval` вешал бы его навсегда. Кто хочет дождаться хвоста в тесте — двигает время.
- **Тесты**: под капотом обычные `setTimeout`/`clearTimeout`, `vi.useFakeTimers()` работает без специальной поддержки. Инжектируемых часов не заводим, пока не появится потребитель, которому фейк-таймеров мало.

### 4.4 Семантика по операторам

- `debounce` — trailing по умолчанию; `{ leading: true }` — первое срабатывание сразу, дальше тишина до паузы.
- `throttle` — trailing по умолчанию (последнее значение окна не теряется); `{ leading }` доступен.
- `delay` — фиксированная задержка каждого срабатывания, без схлопывания; `ms` может быть функцией от payload.
- `interval` — `active` per-scope; `start` в активном интервале — no-op; dispose владельца останавливает все скоупы. `{ leading: true }` — тик сразу при старте.

## 5. Событийная алгебра

### 5.1 `once`

```ts
const shown = once(bannerTrigger);                  // Event<T>, первое срабатывание на скоуп
const shown = once(bannerTrigger, { reset: navigate });
```

Флаг «уже стрелял» — **стор** (не dependency): это семантическое состояние, и SSR-снапшот обязан его переносить — баннер, показанный на сервере, не должен показаться второй раз после гидрации.

### 5.2 `previous`

```ts
const $prev = previous($route);          // Store<T | undefined>
const $prev = previous($route, seed);    // Store<T | S>
```

Однострочник, который нельзя написать на `computed` (ему нужна память), и который каждый проект пишет руками через `subscribe` — с багом про скоуп примерно всегда. Здесь скоуп-корректность бесплатна: `subscribe` отдаёт `(value, scope)`, предыдущее значение пишется в стор того же скоупа.

### 5.3 `reset`

```ts
reset({ clock: logout, target: [$user, $cart, $draft] });
```

Единственный оператор, которому нужно новое от ядра: `initialValueOf(store)` из `@virentia/core/internal` (§2). Сброс всех целей — одна транзакция. Отдельного события `store.reinit` на сторе не заводим: сброс — свойство композиции («по logout сбросить вот эти»), а не отдельного стора, и размазывать его по сторам значит потерять список сбрасываемого из одного места кода.

## 6. Эффекты: `status`

Пер-эффектные `pending`/`inFlight` уже в ядре, а агрегация по нескольким эффектам — computed-однострочник, то есть по критерию §1 агрегатные операторы не проходят (вырезаны 2026-08-08 после реализации). Остаётся единственный оператор, которого из API эффекта не собрать:

```ts
const $status = status(saveFx);          // Store<"initial" | "pending" | "done" | "fail">
```

- `status` — консолидированная машина состояний для UI («не показывай ошибку, пока не было ни одной попытки»); руками это стор + три реакции. Опция `{ reset: Event }` — возврат в `"initial"` — остаётся: результат `status` — производный стор, `reset` из §5.3 к нему неприменим, так что своя опция — единственный способ выразить «новая сущность на экране, история попыток чужая».

Патроновские `pending({ domain })`/`inFlight` не переносятся: доменов в virentia нет, а агрегация — `computed` (при `||` по булевым вместо суммы счётчиков возможна гонка «один закончил, другой начал» — рецепт в доках это оговаривает).

## 7. Форма пакета

- Сабпас **`@virentia/core/utils`** — по тем же соображениям, что `models` ([dynamic-models §10.4](./dynamic-models.md)): одна версия с ядром, свободная эволюция внутренностей, ноль байт не импортирующим. Каждый оператор — именованный экспорт, tree-shaking пооператорный.
- Зависимостей, кроме ядра, нет. Операторы не трогают kernel-приватность — всё строится на публичной поверхности плюс `initialValueOf` из `internal` (один санкционированный импорт, как `owner` у models).
- Иммиграционная шпаргалка patronum → virentia (включая «не порт» с рецептом) — страница в доках; имена портированного совпадают с patronum намеренно.

### Очерёдность

1. **Время** (`debounce`, `throttle`, `delay`, `interval`) — единственное, что нельзя выразить ядром, и самый частый запрос мигрирующих.
2. **Эффекты** (`status`) — дёшево, сразу полезно.
3. **Алгебра** (`once`, `previous`) — по мере надобности.
4. **`reset`** — последним: тянет добавление в `internal`.

Открытые вопросы: нужен ли `delay` с функцией от payload; `interval` с динамическим `ms` (стором).

Решено при реализации: **initial Store-варианта = декларационный initial источника** — свежий скоуп читает из производного то же, что из источника; скоуп, записанный до первого устаканивания, догоняет через одно окно (живого зеркалирования до первого settle нет намеренно — оно пропускало бы неотдебаунсенные значения); у computed-источника сохранённого initial нет — производный стор начинает с `undefined`.
