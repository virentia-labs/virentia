# Диздок: модели, сущности, индексы и трейты

Сабпас `@virentia/core/models`: декларация моделей через трейты, хранение экземпляров в коллекциях, автоматические индексы, запросы дескрипторами полей, кодеки данных.

---

## 1. Задача

Фабрика-функция как модель отлично работает на десятках экземпляров и упирается в четыре вещи:

1. **Данные ↔ модель** пишутся руками дважды и расходятся; вложенные сущности нормализуются вручную.
2. **Дочерние модели** живут в `store<Record<Id, Model>>` — в реактивном значении лежат живые юниты: вставка пересоздаёт контейнер, подписчик на список дёргается от изменения любого поля любого ребёнка, снапшот скоупа не сериализуется.
3. **Поиск** — это `computed(() => list.value.filter(...))`: O(n) на изменение и O(n·k) при k фильтрах.
4. **Стоимость экземпляра**: при 1000 моделей на кадр фабрика даёт 15–25 тыс. объектов churn за кадр.

Плюс поперечное: обобщённый код над разными моделями (мультивыбор, drag-n-drop, сохраняемость, оптимистичные обновления) — то есть трейты.

---

## 2. Опора в ядре

- `Scope` = `{ values, handlers, deps }`. Значение стора лежит в `scope.values` по id и только если в него писали ([store.ts](../../packages/core/lib/units/store.ts)) — скоуп уже дешёвый контейнер состояния.
- `computed` кэшируется per-scope, лениво, при первом чтении в скоупе.
- Микроскоуп ([scope/micro.ts](../../packages/core/lib/scope/micro.ts)) — «разделяемые по ссылке карты + приватная часть»; инстанс-скоуп это обобщение той же механики.
- `store.subscribe(fn)` зовёт подписчика как `(value, scope)` — одна подписка на стор, знающая скоуп записи. На этом стоят индексы (§7.2).
- `owner()` — вложенное владение и каскадный dispose: на нём `model` и `children`.
- `dependency()` — не-состояние per-scope, не сериализуется: там живут коллекции и индексы.

Ядру добавляются: цепочка скоупов (родитель → инстанс), признак принадлежности стора модели, пулинг инстанс-скоупов.

## 3. `model` и `staticModel`

Две разновидности с **идентичной формой объявления и идентичной поверхностью использования** — различается только цена экземпляра. Выбор разновидности виден ровно в одном слове и нигде больше.

**Имён у моделей и трейтов нет.** Идентичность — сама сущность: связи указывают на модель значением, трейты сравниваются по ссылке, поля адресуются дескрипторами. Имя можно задать необязательным `name`, и оно влияет ровно на две вещи: подпись в инспекторе и ключ в снапшоте для SSR. Без него инспектор показывает объявление по месту в исходнике, а сериализация коллекций требует имени и скажет об этом, когда до неё дойдёт дело.

### 3.1 Объявление и создание

**`data` одинакова у обеих разновидностей** — это чистая декларация формы, выполняющаяся один раз: она связывает сторы с полями входа через дескрипторы (`Bound<T>`, не значения). Разновидности различаются только тем, как инстанцируются юниты и что видит `setup`:

```
model:        add(props) → сторы создаются на экземпляр по декларации;  setup(self, props-значения) → юниты экземпляра, можно условные
staticModel:  add(props) → значения ложатся в инстанс-скоуп;            setup(self) → статические юниты, один раз
```

```ts
const Todo = staticModel({                    // или model({...}) — data не меняется вообще
  data: (p: Props<{ name: string; done?: boolean }>) => ({
    title: f.string(p.name),              // стор связан с полем входа `name`
    done:  f.boolean(p.done.or(false)),   // опциональный вход, дефолт при отсутствии
  }),
  setup(self) {
    const toggled = event<void>();
    reaction({ on: toggled, run: () => { self.done.value = !self.done.value } });
    return { toggled };
  },
});

const todos = collection(Todo);               // get-or-create в активном скоупе (§6)
const t = todos.add({ name: "Buy milk" });    // вход — форма пропсов (она же Dto, §9)
t.toggled();
t.done.value;                                 // стор — та же поверхность, что self.done в setup
todos.remove(t.id);                           // или t.dispose() — то же самое
```

- Форма модели **стабильна**: полей «иногда есть, иногда нет» не бывает — иначе ломаются дескрипторы, индексы и кодек. Опциональность данных — типом поля (`f.date().optional()` → стор с `Date | null`), а не наличием поля.
- Пер-инстансная вариативность — привилегия `setup(self, props)` динамической модели, и только для **юнитов**: по значениям пропсов можно условно создать событие, реакцию, эффект. У `staticModel` `setup(self)` пропсов не получает — в once-run коде per-instance значений не существует.
- `data: {...}` объектом — шорткат: поля связаны со входом по именам, дефолт делает ключ опциональным (`f.boolean(false)` ≡ `f.boolean(p.done.or(false))`). Локальное поле, не участвующее во входе, помечается `.local()`; в функциональной форме локальность выражается просто несвязанностью.

Правила, общие для обеих разновидностей:

- **Отдельного глагола загрузки нет — любой вход данных это `add`** (`Todo.create(props)` — сахар над ним; у `children.one` по природе одиночности — `create`/`clear`, §5.1). `add` — апсёрт по id с двумя формами входа: `Dto<M>` — создание (обязательны все ключи без дефолтов) и `{ id } & Partial<Dto<M>>` — мерж присутствующих ключей (PATCH-ответы и WS-дельты из коробки); частичный вход с неизвестным id — dev-ошибка, называющая недостающие ключи. Массив: возвращает экземпляры в порядке входа (созданные и смерженные), исполняется одной транзакцией, ошибка элемента откатывает батч.
- **Форма входа одна** — тип пропсов (слитый из пропсов модели и её трейтов, §9.1).
- **`id` есть у каждой модели**: автогенерируется, переопределяется во входе (серверные данные сохраняют свои id).
- Свободной фабрики (`model((props) => {...})`) нет: замыканные сторы не дают ни дескрипторов, ни индексов, ни кодека. Произвольная императивная фабрика — это `owner()` (после переезда §10.4 — санкционированный импорт из `@virentia/core/internal`).

**Инстанс-API** — фиксированная малая поверхность на каждом экземпляре: `id`, `key` (§10.1), `alive` (§3.5), `json()` (§9.1), `dispose()`, `rebind(newId)` (§10.1), `onCleanup(fn)` (внешний ресурс — подписка, маркер, сокет — привязывается к жизни экземпляра; выполняется при dispose после гейта `restrict`, пока поля читаемы; возвращает отмену; ленивое хранилище — платят только регистрирующие); имена зарезервированы (§4.6). Та же поверхность доступна на `self` **внутри тел юнитов** модели: реакция или эффект выполняется в инстанс-скоупе конкретного экземпляра, поэтому `self.json()` / `self.rebind(...)` бьют именно в него — тем же механизмом, что `self.done.value`, включая сохранение амбиентного скоупа через `await` эффекта. Каноничный поток сохранения поэтому живёт внутри модели: эффект `save` делает `api.save(self.json())` и `self.rebind(saved.id)`. В теле `setup` напрямую (вне юнита) инстанс-API нелегален — в статической модели там ещё нет ни одного экземпляра; dev-ошибка «нет экземпляра в контексте», правило одно на обе разновидности ради переносимости.

**Семантика мержа** (вход с известным id): присутствующий ключ авторитетен, отсутствующий не трогает ничего. Для вложенных связей: присутствующий массив `children.many` — пер-детский апсёрт **плюс сверка** (дети, отсутствующие в массиве, диспозятся; порядок массива — новый порядок); присутствующий объект `children.one` — мерж при том же id, замена при другом или отсутствующем, явный `null` — `clear()` (ошибка «create при живом ребёнке» охраняет только императивный `profile.create()`, кодек сверяет молча). `{ replace: true }` — пер-инстансная полная замена: связанные ключи выставляются из входа (отсутствующие опциональные — в дефолты), локальные поля не трогаются; экземпляры, отсутствующие во входном массиве, не удаляются.

Что даёт `model` сверх голого `owner`: владение и каскад из коробки, группировка в инспекторе, кодек по форме (§9), коллекция и запросы.

### 3.2 Механика `staticModel`

Юниты создаются один раз на объявление; экземпляр — скоуп: `values` свой (ленивый), `handlers`/`deps` — по ссылке от родителя, плюс `parent`. **Инстанс-скоуп всегда привязан к настоящему скоупу**: создание требует активного скоупа или явного `{ scope }`, ошибка — в стиле `requireActiveScope`.

**Маршрутизация чтения и записи** — по статической принадлежности, вычисленной один раз при объявлении:

```
modelDef.locals: Set<storeId>          // поля модели и всех её трейтов

lookup(store, scope):
  scope.modelDef.locals.has(store.id)  →  scope.values    // поле экземпляра
  иначе                                →  scope.parent    // приложенческий стор
```

Один `Set.has` на чтение, без обхода цепочки. В `store.ts` доступ к `scope.values` заворачивается в `readValue/writeValue(scope, id)`.

### 3.3 Ограничения статической модели

`setup` выполняется один раз, поэтому нельзя замыкаться на данные экземпляра (только `self.<поле>`), создавать юниты по условию от данных экземпляра и держать per-instance состояние в переменной замыкания. Замыкание на изменяемую переменную в `setup` — **dev-throw, а не предупреждение**: протекание состояния между экземплярами — наименее отлаживаемый класс багов, предупреждение о нём проматывается.

Пер-инстансные **внешние** ресурсы при этом легальны: тело юнита (где есть амбиентный экземпляр) подписывается наружу и отдаёт отписку в `self.onCleanup(...)` (§3.1) — без стора под функцию и без пер-инстансных юнитов.

Переезд `model` ↔ `staticModel` не трогает ни call sites, ни `data` (она идентична по построению). Единственное, что может потребовать правки, — `setup`, если он использовал пропсы для условных юнитов: это ровно та возможность, которой у статической модели нет по определению.

Расширение отдельного экземпляра (`instance.extend`) не поддерживается: оно возвращает per-instance аллокации, ломает индексы (они держатся на «поле = один стор на коллекцию»), кодек (форма перестаёт быть формой модели) и пулинг (переиспользуемый скоуп должен иметь фиксированную форму). Уникальный набор юнитов — это `model`; опциональная часть у всех — обычное поле, стоящее одну запись в `Map` только у тех, кто в него писал.

### 3.4 Реакции: одна семантика, две реализации

Семантика реакций **одинакова в обеих разновидностях**: реакция модели, подписанная на внешний стор, срабатывает **для каждого живого экземпляра**.

- В `model` это происходит само: юниты per-instance, значит и подписка per-instance.
- В `staticModel` библиотека делает **широковещательную подписку**: одна подписка на внешний стор; при изменении она обходит живые экземпляры модели в скоупе, где произошла запись, и запускает реакцию в инстанс-скоупе каждого. Скоуп записи нормализуется вверх до ближайшего не-инстансного (инстанс-скоупы не бывают домом коллекций — запись из чужого экземпляра широковещается по его приложенческому скоупу). Обход идёт внутри одной транзакции, поэтому индексы пересчитываются один раз (§7.3).

Никаких предупреждений и никакой смены поведения при переезде между разновидностями: то, что срабатывало на экземпляр, срабатывает на экземпляр.

Цена честная: изменение внешнего стора при N живых экземплярах — N прогонов реакции (столько же, сколько у `model`; дешевле только одна подписка вместо N). Дешёвая pull-альтернатива остаётся прежней — `computed`, который пересчитывается лениво и только у тех экземпляров, которые читают. Инспектор показывает стоимость широковещательных реакций (число прогонов за транзакцию), чтобы горячие места были видны.

### 3.5 Цена экземпляра и пулинг

| | `model` | `staticModel` |
|---|---|---|
| Объектов на экземпляр | ~5 юнитов × (узел + замыкания + `next`) ≈ 15–25 | скоуп + ленивая `Map` + записи ≈ 2–7 |
| Рёбер графа на экземпляр | по числу реакций и computed | 0 — граф построен один раз |
| Создание | аллокации, подписки, регистрация | запись значений полей |
| Уничтожение | dispose владельца, отписки, разрыв рёбер | дроп записей, снятие из индексов |

При постоянной текучке коллекция держит free-list уничтоженных инстанс-скоупов и переиспользует `Scope` + `Map` (`clear()` вместо новой). Условия безопасности:

- **поколения**: хендл это `{ slot, generation }`, обращение к устаревшему даёт ошибку «entity was disposed», а не чтение чужих данных;
- **`entity.alive`** — дешёвая реактивная проверка поколения, чтобы потребитель мог деградировать корректно, не оборачивая каждое чтение в try;
- в dev ошибка «entity was disposed» несёт **стек диспоза** («disposed at columns.remove (board.ts:42)») — иначе throw стреляет в невиновном рендере, а улика о виновнике уничтожена.

## 4. Трейты

Трейт — смесь интерфейса и абстрактного класса: объявляет данные (свои и требуемые), требуемое поведение и поведение по умолчанию. Данные модели объявляются только полями `data` — своими или трейтовыми.

### 4.1 Анатомия — одна на трейт и модель

```ts
const Selectable = trait({
  requires: {                                 // требования — модель или другой трейт обязан дать
    selected: f.boolean(),                    //   поле
    canSelect: fn<() => boolean>(),           //   поведение
  },

  data: {
    lastSelectedAt: f.number(0).local(),      // собственное состояние трейта, вне входа
  },

  setup(self) {
    const toggle = event<void>();

    reaction({
      on: toggle,
      run: () => {
        if (!self.canSelect()) return;
        self.selected.value = !self.selected.value;
        self.lastSelectedAt.value = now();
      },
    });

    return { toggle };
  },
});
```

Хозяева анатомии различаются минимально: `requires` есть только у трейта. Всё остальное — `with`, `data`, `setup` — пишется одинаково, поэтому вынос полей из модели в трейт — копипаста, а не переспеллинг.

**Требование и объявление — задачи разного класса, поэтому у них разные секции.** `requires` только требует (схему поля или сигнатуру поведения) и никогда не хранит; `data` только объявляет и всегда хранит. Читая трейт, видно сразу: что он принесёт с собой, а чего ждёт от композиции.

`data` трейта может быть функцией его собственных пропсов — так трейт объявляет свой кусок формы входа (§9.1):

```ts
const Timestamped = trait({
  data: (p: Props<{ created_at: string; updated_at: string }>) => ({
    createdAt: f.date(p.created_at.map(parseDate, toIso)),
    updatedAt: f.date(p.updated_at.map(parseDate, toIso)),
  }),
});
// каждая модель с Timestamped получает created_at/updated_at во входе — объявлено один раз
```

### 4.2 Модель — композиция трейтов и связка

```ts
const Todo = staticModel({
  with: [Selectable, Archivable, Timestamped],
  data: {
    title:    f.string(),
    selected: f.boolean(false),     // объявление закрывает требование Selectable
  },
  setup(self) {
    // всё из трейтов лежит прямо в self: toggle из Selectable, archived из Archivable, updatedAt из Timestamped
    reaction({ on: self.toggle, run: () => { self.updatedAt.value = now() } });

    return { canSelect: () => !self.archived.value };   // реализация абстрактного поведения
  },
});

const todo = collection(Todo).add({ title: "…", created_at: "2026-08-05", updated_at: "2026-08-05" });
todo.toggle();        // и на экземпляре — просто член
```

**Всё из трейтов протекает в `self` и в экземпляр.** Квалифицированного доступа нет: член трейта неотличим от собственного члена модели — ни в `setup`, ни снаружи, ни в типах.

**Происхождение члена обязано быть восстановимым** (требование к реализации типов, проверяемое как пробы §5.4): go-to-def на `todo.toggle` приземляется в объявление `Selectable`, а не в машинерию пакета; инспектор показывает, из какого трейта пришёл член; таблица член→трейт (она и так есть у проверки коллизий) доступна в dev.

**`setup` — и модели, и трейта — не создаёт сторов**: `store`/`reactive` в нём — ошибка объявления («состояние живёт в `data`»). События, эффекты, реакции, `computed` — можно.

### 4.3 Инстанцирование

Трейт инстанцируется **один раз на пару (трейт, модель)**: не глобально, потому что его `setup` ссылается на абстрактные члены, а они у разных моделей разные сторы; и не на экземпляр — иначе теряется весь смысл статической модели. У динамической модели трейт инстанцируется на экземпляр — форма и кодек те же, отличается цена.

Таблица членов модели собирается один раз при объявлении, поэтому доступ к `todo.toggle` — обычное свойство, без поиска по трейту в рантайме.

### 4.4 Обобщённый код

```ts
function selectAll<M extends Impl<typeof Selectable>>(c: Collection<M>) {
  for (const m of c) m.toggle();
}
```

Трейт фигурирует только в ограничении типа — в теле работают обычные члены. Ошибка несоответствия называет недостающий член: «модель не реализует трейт: нет `canSelect: () => boolean`» (с `name` или местом объявления вместо имени).

### 4.5 Параметризованные трейты

Параметризация целиком ложится на **штатные генерики TypeBox** — своего механизма дырок нет. Плейсхолдер в схеме поля — это `Type.Argument` (позиционный аргумент схемы), применение трейта — инстанцирование: аргументы передаются значениями-схемами, ровно как в обычных дженериках.

```ts
const Keyed = trait({
  requires: { code: f.arg(0) },         // Type.Argument(0) — плейсхолдер TypeBox
  setup(self) {
    return { sameKeyAs: (other: Impl<typeof Keyed>) => equals(self.code.value, other.code.value) };
  },
});

const Todo = staticModel({
  with: [Keyed(f.string())],            // применение: аргументы позиционно, схемами
  data: { code: f.string("") },
});
// поле не может называться key — это инстанс-API (§3.1), закон §4.6 это ловит
```

- **Применение — не фабрика**: `Keyed(f.string())` инстанцирует один и тот же трейт, как инстанцируется дженерик; идентичность трейта одна на все применения, поэтому обобщённый код принимает «любой `Keyed`».
- **Арность не пишется руками** — выводится из формы (максимальный индекс аргумента); незакрытый аргумент при применении — ошибка с его позицией.
- **Аргументы составные**: `f.list(f.arg(0))`, `f.record(f.arg(1))` — подстановка идёт вглубь схемы средствами самого TypeBox.
- Для параметров-значений (не типов) аргумент — просто второй параметр применения: `Keyed(f.string(), { compare })`.

### 4.6 Один закон имён

**Требовать (`requires`) могут сколько угодно участников композиции; объявлять (`data` / возврат `setup`) — ровно один.**

```ts
const Selectable = trait({ requires: { selected: f.boolean() } });   // «мне нужно selected»
const Hoverable  = trait({ requires: { selected: f.boolean() } });   // «и мне» — требования совместимы

const Todo = staticModel({
  with: [Selectable, Hoverable],
  data: { selected: f.boolean(false) },   // единственное объявление закрывает оба требования
});
```

- требование × требование — унифицируются при совместимых схемах; несовместимые — ошибка с именами обоих трейтов;
- требование × объявление — выполнение;
- объявление × объявление (два `data`-поля, две реализации поведения) — коллизия: ошибка при объявлении модели, лечится алиасом `with: [Named.as({ name: "label" })]`;
- требование, оставшееся без объявления, — ошибка: «модель не даёт `selected: boolean` (требует Selectable)»;
- `data` модели участвует наравне с трейтами; имена, совпадающие с API определения (`create`, `name`, …), — та же ошибка с тем же лечением; модификаторы объявления (`.indexed()` и т.п.) живут только у объявляющего.

Квалифицированного доступа как запасного выхода нет намеренно: он сделал бы члены трейтов гражданами второго сорта.

### 4.7 Встроенные трейты

- `Identifiable` — поле `id` (автогенерация, переопределение во входе `add`); встроен в каждую модель, вручную указывается только как граница обобщённого кода (`Impl<typeof Identifiable>`).
- `Disposable` — хуки жизненного цикла экземпляра.

Отдельных `Indexable`/`Serializable` нет: индексируемость и сериализация — модификаторы поля (§7.1, §9.1), им не нужен трейт-маркер.

### 4.8 Схема полей: ядро — TypeBox, слой поля — наш

Свою схема-библиотеку не пишем. Каждый дескриптор поля несёт внутри **TypeBox-схему** (`TSchema`): типы значений, `Static<>`-вывод, валидация и JSON Schema берутся оттуда, а не изобретаются. `f.*` — тонкие шорткаты над `Type.*` плюс тот слой, которого в схеме значений нет и быть не может: дефолт, биндинг ко входу, индексы, связи.

Упаковка: `@sinclair/typebox` — **опциональный peer** ядра, его импортируют только модули сабпаса `/models`. Кто сабпас не трогает — не ставит и не бандлит TypeBox вовсе; кто трогает — ставит peer сам (без него импорт сабпаса упадёт разрешением модуля с именем пакета в ошибке).

```ts
f.string()            // Type.String() внутри
f.number(0)           // Type.Number() + дефолт
f.integer()           // Type.Integer
f.boolean()
f.null() / f.any() / f.unknown()
f.date()              // хранит Date; на проводе ISO-строка (Type.String({ format: "date-time" })),
                      // парс/сериализация встроены, переопределяются .map
f.literal("a")        // Type.Literal
f.enum(["a", 1])      // Type.Union of literals (строки и числа)
f.array(inner)        // Type.Array (f.list — алиас)
f.tuple([a, b])       // Type.Tuple — фикс-длина, попозиционные типы
f.union([a, b])       // Type.Union значений
f.intersect([a, b])   // Type.Intersect
f.record(inner)       // Type.Record
f.object({ ... })     // Type.Object из ШЕЙПА полей (или готовая TSchema) — данные-значения, не модель!
f.recursive(self => …) // Type.Recursive — деревья одним значением
f.from(schema)        // любая готовая TSchema — сложные значения пишутся голым TypeBox
f.arg(0)              // плейсхолдер генерика (§4.5) — Type.Argument, штатный TypeBox
```

**Любой тип собирается из `f.*`**: позиция элемента у каждого комбинатора принимает поле **или** голую TypeBox-схему (`f.from`/`Type.*` — листья последней инстанции). Комбинаторы композируют не только схемы, но и **кодеки значений** — рекурсивно: `f.array(f.date())` хранит `Date[]`, на проводе `string[]`, конверсия поэлементная; `f.object({...})` — по ключам; `f.tuple` — по позициям. Простые формы кодек не аллоцируют вовсе. Пользовательский `.map` на поле **забирает конверсию целиком** (получает сырой провод и владеет обеими сторонами — и валидацией: schema-check его ключ пропускает). Трансформы внутри `f.union`/`f.intersect`/`f.recursive` — именованная ошибка декларации: ветку конверсии там выбрать нельзя, `.map` вешается на всё поле. `.meta({...})` вливает аннотации в опции TypeBox-схемы — канал метаданных формата для кастомных кодеков (§9.3: бинарные раскладки и т.п.) через рефлексию.

Наш слой — только модификаторы, и у каждого одна зона ответственности:

| Модификатор | Зона | Смысл |
|---|---|---|
| дефолт аргументом / `.or(v)` | вход | ключ опционален, при отсутствии — значение |
| `.optional()` | значение | хранится `T \| null`, ключ входа опционален |
| `.map(in, out?)`, `.inOnly()` | биндинг | преобразование провода (§9.1) |
| `.local()` | биндинг | поле вне входа (объектная форма, §3.1) |
| `.indexed("eq" \| "ord")`, `.unique()` | индекс | §7.1 |

`refs`/`children`/`inverse` — не схемы значений, а схемы **связей**: у них своя таблица (§5.1), в TypeBox им эквивалента нет, и это единственная часть слоя, которая не сводится к обёртке.

Валидация входа: `add()` проверяет вход по TypeBox-схеме — в dev всегда, в prod по опции. Ошибка называет поле и модель. Из тех же схем бесплатно выводится JSON Schema всей формы входа (`Dto`) — для OpenAPI, контрактных тестов, генерации моков.

## 5. Ссылки между моделями

### 5.1 Два вида связи

`children` — композиция (время жизни привязано к родителю), `refs` — ассоциация (цель живёт сама по себе). Кардинальность — модификатором `.one`/`.many`.

Обе связи — всегда про **модель**: дочернюю (`children`) или независимую (`refs`). Поле-объект с данными связью не является — это просто данные (`f.object`, при желании поверх `@virentia/core/mutable`).

```ts
board.columns          // children.many → Query<Column>, порядок вставки
user.profile           // children.one  → { value: Handle<Profile> | null, create(props), clear() }
post.author            // refs.one      → стор с Handle<User> | null
post.tags              // refs.many     → набор с add/remove/ids и запросами
```

| | `children` | `refs` |
|---|---|---|
| Время жизни | привязано к родителю: dispose родителя → рекурсивный dispose детей | независимое |
| Владелец | `owner` родительского экземпляра | своя коллекция |
| Хранение | общая коллекция модели-ребёнка + индекс по родителю | fk-поле (`.one`) или набор id (`.many`) |
| Кодек | встроенно: `.many` — массив, `.one` — объект | по id |
| Удаление цели | n/a | `restrict` \| `nullify` \| `orphan` |
| Порядок | `.many` держит порядок вставки | порядок вставки для `.many` |

Дети физически лежат в общей коллекции своей модели, а «дети конкретной борды» — это запрос по индексу родителя. Так переиспользуется весь механизм индексов, память остаётся плоской при тысяче создания за кадр, а глобальные запросы поверх детей («все просроченные карточки во всех бордах») работают сами собой. Родительство настоящее: родительский fk связан с `owner`-цепочкой, dispose каскадит — этим `children` и отличается от «`refs` с индексом».

Дети создаются только через поверхности, где родитель в руках явно: `board.columns.add(props)` и `user.profile.create(props)` (и то же через `self` внутри setup) либо загрузка данных, где родитель известен. `Column.create(...)` на модели-ребёнке — всегда ошибка, указывающая на `.add`. У `children.one` создание при живом текущем ребёнке — ошибка (`clear()` диспозит явно). Никакого неявного «активного родительского контекста» нет.

**Порядок детей.** `children.many` — список, а не множество: группа родительского индекса хранится упорядоченной, `move(id, index)` — для перестановок, и порядок ездит через кодек сам собой, потому что дети сериализуются массивом — порядок массива и есть порядок. Явный порядок (у бэкенда есть поле позиции) не требует от либы ничего: это обычное поле в `data` + `sort` в запросе.

Вложенность произвольная, каскад идёт по цепочке владельцев. Циклы в `children` запрещены и проверяются при инициализации; циклы в `refs` — норма.

### 5.2 Объединения

Лента, дерево слоёв, результаты поиска — коллекции разнородных элементов. Объединение позиционное — идентичность варианта, как и всюду, ссылка на модель, а не строковый ключ:

```ts
const FeedItem = union(Post, Ad, Story).by((json) =>
  "likes" in json ? Post : "budget" in json ? Ad : Story,
);
const feed = collection(FeedItem);           // get-or-create, как у модели (§6)

feed.where(FeedItem.createdAt.gte(today)).match(
  [Post,  (p) => p.likes.gte(100)],
  [Ad,    (a) => a.active.eq(true)],
  [Story, () => true],
);
```

- **`match` — по ссылкам моделей**, исчерпывающий: пропущенный вариант — ошибка компиляции. Аргумент ветки — дескрипторное пространство варианта; ветка возвращает предикат по нему либо литерал `true`/`false` (весь вариант подходит/не подходит).
- **Общий член объединения** существует ⇔ каждый вариант несёт его **из одного и того же трейта по ссылке** (`FeedItem.createdAt` ⇐ все варианты с `Timestamped`). Совпадение имён общности не даёт — иначе через чёрный ход вернулась бы строковая идентичность. Запрос по общему члену не требует `match`.
- **`by` — дискриминатор входа**: обычная функция `(json: Dto<typeof Post> | Dto<typeof Ad> | …) => Model`, решающая, чей это json, — без неё `feed.add(json)` не знает варианта, и её отсутствие при попытке `add` — ошибка типов. Порядок разрешения: вход с известным id сначала ищется по коллекциям вариантов и мержится в найденный **без** участия `by`; `by` решает только для неизвестных id — полных созданий, где дискриминация по форме корректна. Если id найден в варианте X, а `by` указывает на Y, — dev-ошибка: миграции варианта нет. Обратного дискриминатора нет: каждый вариант сериализуется своим кодеком, а различительное поле — его обычное поле.
- **Хранение**: экземпляры физически живут в коллекциях своих моделей; union-коллекция — представление поверх них (`add` маршрутизирует через `by`, запрос — слияние по-вариантных результатов, сортировка по общему члену — k-way merge по индексам вариантов). `refs.many(FeedItem)` / `children.many(FeedItem)` хранят пары (модель, id).

### 5.3 Обратная сторона: `inverse`

**Простая форма — дефолт.** `refs.one(User)` — это «просто ссылка на инстанс», `children.many(() => Column)` — «просто дети»: объявил — работает, ни `unique`, ни `inverse`, ни обратных сторон знать не нужно. Всё в этом разделе — опциональные уточнения для тех, кому нужна обратная навигация или констрейнт 1:1; не объявил — не заплатил.

По умолчанию каждое связанное поле — самостоятельная переменная; **связанных пар нет**. Двунаправленность — отдельный механизм: `inverse` объявляет поле-**вид** над владеющей стороной.

```ts
// post.ts — владеющая сторона: хранит fk, сериализуется
export const Post = staticModel({
  data: { title: f.string(), author: refs.one(() => User) },
});

// user.ts — обратная сторона: одна строка, ноль хранения
export const User = staticModel({
  data: { name: f.string(), posts: inverse(() => Post.author) },
});

post.author;   // стор с Handle<User> | null — владеющая сторона
user.posts;    // Query<Post> — вид над fk-индексом author
```

Свойства, из которых всё следует:

- **Хранилища у `inverse` нет.** Это вид над обратным индексом владеющего поля — а обратный индекс у fk и так есть (§7.1). Значит, рассинхронизация двух сторон **невозможна по построению**: источник истины один.
- **Сериализация тривиальна**: владеющая сторона пишет id (или набор id, или встроенных детей — §9), `inverse` не сериализуется никогда. После `add` виды консистентны сразу, потому что читают индекс, а не собственную копию.
- **Связывание на inverse-виде — `link`/`unlink`**, не `add`/`remove`: `user.posts.link(post)` ≡ `post.author.value = user`, `user.posts.unlink(post)` ≡ `nullify`. Имена намеренно другие: `remove` на Query — массовый dispose (§8), перегружать его связыванием нельзя. Операции связывания принимают экземпляр или id — одно правило для `refs.many.add` и `link`/`unlink`. Инверс кардинальности one — вид со `.value`; запись `column.board.value = otherBoard` — перенос к другому родителю.
- **Родитель ребёнка** — тот же механизм: fk родителя у `children` существует всегда (скрыто); `inverse(() => Board.columns)` — санкционированный способ сделать его видимым. Видимый или нет, в кодек он не попадает, потому что дети сериализуются встроенно.
- Самоссылки — через `Self`: `arrows: children.many(Self)`, `parent: inverse(() => Self.arrows)`.

Все кардинальности — одним механизмом:

| Связь | Владеющая сторона (хранит, сериализуется) | `inverse` даёт | Механика |
|---|---|---|---|
| many-to-one | `Post.author: refs.one(() => User)` — fk | `User.posts` → `Query<Post>` | обратный fk-индекс |
| one-to-one | `Profile.user: refs.one(() => User).unique()` | `User.profile` → `Handle \| null` | уникальный fk-индекс; второй Profile на того же user — ошибка констрейнта при записи |
| many-to-many | `Post.tags: refs.many(() => Tag)` — набор id | `Tag.posts` → `Query<Post>` | обратный индекс по элементам набора |
| дети (one-to-many) | `Board.columns: children.many(() => Column)` | `Column.board` → `Handle \| null` | родительский fk ребёнка |

Кардинальность `inverse` выводится, юзер её не пишет: от `children.many` — one (родитель один по построению); от `refs.many` — many; от `refs.one` — many, а с `.unique()` — one. `.unique()` — обычный модификатор поля (валидация на записи + структура индекса), полезный и вне связей.

Отдельной junction-модели для many-to-many нет: набор id живёт на владеющей стороне, обратный индекс поддерживает либа. Если ребру нужны собственные данные (вес, дата добавления) — это честная модель между двумя (`Membership` с двумя `refs.one`), и обе стороны получают `inverse` уже на неё.

Итого двунаправленная связь стоит одну строку на ту сторону, которая нужна видимой, ноль строк — если не нужна, и не создаёт ни одной возможности рассогласования.

### 5.4 Цель связи, `Self` и циклы

Позиция цели в `refs`/`children` принимает ровно три формы: **модель или объединение значением** (`refs.one(User)` — когда цель объявлена выше), **санк** (`refs.one(() => User)` — цикл или forward-ссылка), **маркер `Self`** (самоссылка). `inverse` принимает санк владеющего **поля** (`() => Post.author`). Ничего другого позиция цели не означает.

**`Self`** — импортируемый маркер (`import { Self } from "@virentia/core/models"`); заглавная буква намеренна: параметр `setup(self)` остаётся строчным, затенение невозможно. В модели `Self` — сама модель; в трейте — модель, реализующая трейт (разрешается на каждое применение — ровно `Self` из Rust). Пути по маркеру (`Self.arrows`) типизированы по объявленным членам: опечатка — ошибка компиляции, а не отложенная загадка.

**Взаимные циклы не стоят ничего** — ни аннотаций, ни имён, ни сборки. Это держится на инварианте сигнатуры, проверенном компилятором (TS 6.0.3; пробы: единичный файл, кросс-файловые циклы, стресс 12 моделей × 20 переходов — артефакты в scratchpad `mutual/`):

```ts
// НЕЛЬЗЯ — вывод M форсирует возврат санка в момент объявления → TS7022/7024:
declare function refs<M>(f: () => M): Ref<M>;

// НУЖНО — F это тип ФУНКЦИИ, её возврат TS вычисляет лениво:
declare function refs<F extends () => void>(f: F): Ref<F>;
```

Тип функционального выражения — сигнатура с ленивым возвратом; `Ref<F>` уносит её нераскрытой, и объявление завершается, не заглянув в цель. Разворачивается связь per-property (`F extends () => infer M`) при первом обращении, когда обе константы объявлены. Ограничение сигнатуры фиксировано: ленивость переживают ровно `() => void`, `() => any` и отсутствие ограничения (`() => unknown` и `() => object` — ломают).

Страховки — часть дизайна, не фольклор:

- рантайм валидирует результат санка при первом вызове: «refs(): thunk returned X, expected a model»;
- если `ReturnType<F>` — не модель, поле типизируется брендированной ошибкой на объявлении, а не простынёй mapped-типов на месте использования;
- пробы из scratchpad становятся CI-контрактом на версии TS (механика опирается на недокументированную ленивость чекера);
- санк не исполняется в момент объявления (TDZ) — только при первой навигации, с кэшем.

Границы: внутри одной компиляции всё строго; declaration emit обрезает цикл на глубине 2 в `/*elided*/ any` — **публиковать библиотеку моделей поверх этого вывода нельзя** (там нужны аннотации), `isolatedDeclarations` несовместим. Для приложений и монорепо ограничений нет.

Резолвинг в рантайме: коллекции живут в скоупе приложения и заводятся по определению модели, поэтому `post.author` — поиск в коллекции `User` текущего скоупа.

## 6. Коллекции

Контракт:

- **`collection(Todo)` — get-or-create** на пару (скоуп, определение): повторный вызов в том же скоупе возвращает ту же коллекцию; два скоупа — две независимые коллекции при одном определении. Для объединения (`collection(FeedItem)`) — то же самое, но результат — представление поверх коллекций вариантов (§5.2).
- **Коллекция — единственная поверхность создания и владелец экземпляров**: `todos.add(props) → instance`, `todos.get(id)` (реактивный вид одного экземпляра — примитив под `useModel(todos.get(id))`, резолвит и форвардинг §10.1), `todos.remove(id)` (≡ `instance.dispose()`), каскад по `children`. `Todo.create(props)` — сахар над коллекцией активного скоупа.
- **Коллекция — это `Query` без фильтра**: `todos.items`, `todos.ids`, `todos.count`, итерация — тот же интерфейс, что у любого запроса (§8). Отдельного словаря (`size` и т.п.) нет.
- **Хранилище — не стор**: слот в скоупе приложения, `Map<Id, Instance>`. Вставка не пересоздаёт контейнер; подписчик на список не дёргается от изменения поля ребёнка.
- Коллекция, созданная неявно (первым обращением навигации §5.4), помечается в инспекторе; dev предупреждает, если ссылка разрешилась в автосозданную коллекцию, в которую никто не писал — это почти всегда «данные загружены не в тот скоуп».

## 7. Индексы

### 7.1 Объявление у поля

Индексируемость — свойство поля, объявляется рядом с полем и приезжает с трейтом во все его модели:

```ts
data: {
  title:    f.string(),
  done:     f.boolean(false).indexed(),        // хеш-индекс
  priority: f.number(0).indexed("ord"),        // сортированный: диапазоны и orderBy
}
```

`children`/`refs` объявляют свой fk-индекс сами — обратные связи и `inverse` не стоят пользователю ни строчки. Других мест управления индексами нет: **объявление ≠ материализация**, физическая структура строится лениво при первом запросе, который её использует, и выбрасывается, если запросов нет. Ленивость — вся политика; коллекционных перекрытий (`drop`/`add`) не существует. Исключение — **структурные индексы**: fk-индексы `children`/`refs` и все `.unique()` поддерживаются жадно с создания коллекции — на них держатся каскад, `inverse`, перепись fk при `rebind` и констрейнты записи, им нельзя быть «ещё не построенными».

### 7.2 Почему индексы здесь дешёвые

Это внутренняя механика, не API — но она объясняет, зачем статические модели, коллекции и индексы существуют как один механизм.

Чтобы индекс был актуален, кто-то должен узнавать о каждой записи в индексируемое поле. У статической модели поле — **один стор на всю коллекцию** (значения различаются скоупами экземпляров), а подписка на стор в ядре получает `(value, scope)` — то есть уже знает, чей экземпляр записан. Поэтому либе хватает **одной подписки на индексируемое поле**, сколько бы экземпляров ни было, и создание/уничтожение экземпляра не стоит ни одной подписки/отписки — при 1000 за кадр это и есть разница между «работает» и «лежит».

У динамической модели поле — стор на каждый экземпляр, поэтому индексам нужна подписка на каждый экземпляр плюс подписка/отписка на каждое создание. Работает, но дороже: приемлемо на сотнях, неприемлемо на тысячах с текучкой — это причина переехать на `staticModel`, а не запрет пользоваться `model`.

### 7.3 Структуры

- `eq`: `Map<value, IdSet>`; `IdSet` — `Set` до порога, дальше упакованный отсортированный массив.
- `ord`: отсортированный массив ключей и параллельный массив id, `lowerBound`/`upperBound`. Вставки буферизуются и сливаются при первом запросе после транзакции: тысяча вставок за кадр даёт один merge вместо тысячи splice.
- Пересечение: кандидаты из самого селективного индекса, остальное — остаточным предикатом.

### 7.4 Диагностика

Если запрос повторно идёт полным сканом по неиндексированному полю, dev-режим пишет: «query on `priority` (todo.ts:14) scanned 12 480 rows × 20 runs — add `.indexed("ord")`». Индексы не создаются автоматически по факту нагрузки — непредсказуемая память хуже честного предупреждения.

## 8. Запросы

**Ровно две поверхности у поля.** На определении `Todo.done` — дескриптор (что за поле, какого типа, с каким индексом). На экземпляре `todo.done` — стор, тот же самый, что `self.done` внутри `setup`: читается и пишется через `.value` в любом месте кода. Голое значение существует только в проекциях (`select`) и DTO. Инстансных `set`/`update` нет — на одном экземпляре стор и есть путь записи; дескрипторная запись живёт только на запросах, где она реально окупается.

**Дескрипторы берутся только у той модели, в которой ищем.** Модель переэкспортирует все свои поля, включая пришедшие из трейтов: `Todo.createdAt` — без импорта `Timestamped`, `Post.author.name` — без импорта `User`, `FeedItem.createdAt` — общий член через сам union (вариантные поля доступны только внутри веток `match`, §5.2). Трейт импортируется, чтобы объявить модель, но никогда — чтобы её искать. Исключение — неоднозначное имя (§4.6), и оно снимается алиасом в месте композиции, то есть тоже остаётся на модели.

```ts
const active = todos
  .where(Todo.done.eq(false))
  .where(Todo.priority.gte(3))
  .sort(Todo.priority.desc)
  .take(50);
```

**Один регистр операторов, включительность в имени**: `eq / neq / gt / gte / lt / lte / between / startsWith / includes`. Сортировка — свойства `asc`/`desc` на дескрипторе. Терминалы запроса — единообразно реактивные свойства: `items`, `ids`, `count`, `first`; проекция — `select(Todo.title)` → `Query<string>` без материализации экземпляров; разовый снимок — `toArray()`.

`where` принимает и **обычный предикат** — `todos.where(t => !t.done.value)` — исполняется остаточным сканом; диагностика §7.4 сама подскажет, когда скан стал горячим и пора переходить на дескриптор. Это осознанный трамплин, а не второй сорт.

Переходы по связям дают join'ы без отдельного механизма:

```ts
posts.where(Post.author.name.eq("Bob"));                       // через refs и fk-индекс
boards.where(Board.columns.some(Column.cards.count.gte(10)));  // через children
```

Массовая правка — та же цепочка, одной транзакцией и с одним обновлением индексов:

```ts
todos.where(Todo.done.eq(false)).set(Todo.done, true);
todos.where(Todo.priority.lt(0)).remove();
```

Результат запроса — per-scope, как у `computed`. **План = форма запроса без значений**; значения предикатов — bind-параметры, а не часть структурного ключа (иначе `startsWith(userInput)` рос бы intern-таблицей на каждый ввод). Мемо-ключ результата — (план, значения, скоуп). Пересчёт батчится на границе транзакции ([kernel/transaction.ts](../../packages/core/lib/kernel/transaction.ts)), идентичность неизменившегося результата стабильна; hit-rate планов и мемо виден в инспекторе.

## 9. Данные ↔ модель

### 9.1 Кодек — это биндинг пропсов, отдельной секции нет

Кодек делает ровно одну работу: какой ключ входа как парсится и в какой стор ложится — и обратно. Эта работа уже сделана объявлением `data` (§3.1): связывание стора с полем входа **и есть** кодек.

```ts
const Todo = staticModel({
  data: (p: Props<{ name: string; created_at: string }>) => ({
    title:     f.string(p.name),                              // ключ name ↔ стор title
    createdAt: f.date(p.created_at.map(parseDate, toIso)),    // парс туда, сериализация обратно
    draft:     f.string(""),                                  // не связан со входом → не на проводе
  }),
});

todos.add(json);         // json: Dto<typeof Todo> — слитый тип пропсов модели и её трейтов
todo.json();             // обратное направление выведено из тех же биндингов
```

- **Форма входа = тип пропсов**, один на создание и загрузку (`add`, §3.1; частичные PATCH-входы — форма `{ id } & Partial<Dto>` там же). Незакрытый ключ пропсов — ошибка компиляции на стороне объявления; поле без биндинга — не на проводе.
- **Обратное направление выводится**: связка «ключ ↔ стор» обратима сама, для трансформаций — второй аргумент `.map(in, out)`. Намеренная односторонность помечается явно: `.map(parse).inOnly()`. Голый одноаргументный `.map` без пометки — dev-диагностика при первом `json()` («поле связано только на вход и опущено из json()»): забытый out-трансформ не должен превращаться в молчаливую потерю данных при сохранении.
- **Трейт приносит свой кусок входа** — `data`-функция трейта с его собственными пропсами (§4.1): `Timestamped` один раз объявляет `created_at`/`updated_at` для всех своих моделей. Слияние — по закону §4.6.
- **Один ключ — один стор.** Склейки из нескольких ключей и вычисления — не работа биндинга, это адаптер (§9.2).

Наружу модель отдаёт `json()` — метод и называется так; протокол `toJSON` реализован поверх него, поэтому `JSON.stringify(todo)` работает сам. `children` сериализуются встроенно (через биндинги модели-ребёнка), `refs` — по id, `inverse` — никогда (§5.3).

Отсюда же SSR (снапшот коллекции — плоские данные), таблица вместо дерева узлов в devtools и `collection.add(fixture)` в тестах.

### 9.2 Чужие и вторичные форматы

Кодек описывает **свой** формат модели. Всё остальное — второй REST-эндпоинт, WS-сообщение, состояние в URL, легаси-импорт — обычная типизированная функция рядом с интеграцией:

```ts
const fromLegacy = (json: LegacyTodo): Dto<typeof Todo> => ({
  name: json.TITLE,                    // ключи — форма ПРОПСОВ модели (§3.1), не поля
  done: json.STATUS === "closed",
});

todos.add(fromLegacy(json));
```

`Dto<typeof Todo>` выводится из объявления, поэтому адаптер проверяется компилятором и не расходится с моделью. Если формат нужен в обе стороны и надолго — возможно, он и есть свой, и ему место в кодеке (§9.1).

## 10. Биндинги и инспектор

### 10.1 React

Новых хуков нет: биндинги — это существующие `component` и `useModel` (плюс `useUnit` для отдельных юнитов). Запросы, экземпляры и коллекции — обычные модельно-подобные объекты, и tracked-чтение работает с ними так же, как с любой моделью.

- **Экранная модель** — `component({ model: OrderScreen, view })` или `useModel(OrderScreen, props)`: определение модели уже является фабрикой `props → экземпляр`, поэтому существующая сигнатура подходит как есть — экземпляр создаётся в предоставленном скоупе (через коллекцию, как любой `add`), пропсы реактивно дописываются, dispose на анмаунте. `component.create()` для controlled-инстансов — без изменений.
- **Пережить анмаунт — флаг `keep`**, а не кэш: `useModel(SettingsScreen, props, { keep: true })` (и `component({ model, keep: true })`). `keep` меняет ровно одно — владельца конца жизни: анмаунт не диспозит, ремаунт находит тот же экземпляр и домерживает пропсы, завершает жизнь явный `remove` или конец скоупа. Кого находит ремаунт: без id во входе — **синглтон на скоуп** (get-or-create единственного экземпляра модели — обычный случай: настройки, единственная форма); с id во входе — экземпляр по id (случай многих удержанных: вкладки, master-detail, id приходит извне — роут, документ). Речь про **штатный `id` модели** (§3.1) — он и так обязан быть у каждого экземпляра; отдельного ключа биндингов не существует. `keep` без id при нескольких живых экземплярах модели — dev-ошибка: неоднозначность вместо молчаливого выбора. Опций `cache`/`key` у новых моделей нет — кэш был теневой коллекцией для инстансов фабрик, которым негде жить; у модели дом есть — её коллекция, и `keep` лишь оставляет экземпляр дома вместо диспоза. `cache` остаётся только в сигнатуре `useModel(factory, props, { cache, key })` для старых функций-фабрик.
- **Запрос в рендере** — `useModel(query)`, включая цепочку, собранную прямо в рендере: `useModel(todos.where(Todo.done.eq(false)).sort(Todo.priority.desc).take(50))` — план интернируется, результат мемоизирован по (план, значения, скоуп) (§8), поэтому пересборка цепочки на каждый рендер не аллоцирует и не требует deps-массивов. Tracked-чтение `query.items` / `query.count` подписывает компонент; рендер — только при изменении множества; ключ строки — `instance.key`.
- **Экземпляр по id** — `useModel(todos.get(id))`: `get(id)` — реактивный вид одного экземпляра; резолвит **алиасы** (форвардинг после `rebind` — компонент со старым id в пропсах или URL продолжает работать), отдаёт `null`, если экземпляра нет или он диспознут (в паре с `entity.alive`, §3.5) — не бросает посреди рендера. Для сущностей коллекций отдельный кэш биндингам не нужен: коллекция и есть кэш — get-or-create по id, экземпляр живёт независимо от маунтов.

**`instance.key`** — стабильный ключ для UI: производится от пары слот+поколение (§3.5), живёт от создания до dispose, **не меняется при смене id** и не совпадает при переиспользовании слота пулом. Списки не ремаунтятся из-за того, что сервер переименовал сущность, и не склеивают строки разных сущностей.

**Смена id — `rebind`, а не алиасы.** `instance.rebind(newId)` атомарно переписывает все fk-ссылки (обратные индексы уже знают всех ссылающихся — O(числа ссылок), без скана) и оставляет **форвардинг-запись** `oldId → newId` до конца жизни скоупа: `collection.get(oldId)` — и значит `useModel(todos.get(oldId))` — продолжает резолвить — компонент, державший старый id (роутер, пропсы), не ломается. В индексы и `json()` форвардинг не попадает никогда, поэтому временные id не утекают на сервер и не дублируют результаты запросов. Правила форвардинга: запись живёт, пока жив экземпляр (dispose удаляет её — таблица ограничена живыми перепривязанными, а не историей); разрешение — только фолбэк (прямое совпадение id в коллекции всегда побеждает); `add` форвардинг не консультирует — он матчит настоящие id, а вход с id, равным живому форвардинг-ключу, снимает эту запись с dev-предупреждением. Автогенерированный id помечен временным и в `json()` не попадает — сервер назначает свой; сериализуются только id, пришедшие извне (вход `add` или `rebind`). Публичного `addAlias` нет: форвардинг — единственная форма алиаса, след `rebind`. Мульти-ключность («найти по slug и по uuid») — не второй id, а второе поле с `.indexed().unique()`.

Оптимистичное создание сквозняком:

```ts
const t = todos.add({ name });             // id сгенерирован
navigate(`/todo/${t.id}`);                 // URL со временным id
const saved = await api.save(t.json());
t.rebind(saved.id);                        // fk переписаны; старый id форвардится до конца скоупа;
                                           // t.key не изменился — строка списка не ремаунтится
```

### 10.2 Vue

Зеркально: те же `component`/`useModel`, поля — сторы, те же `key`/`rebind`-гарантии.

### 10.3 Inspector

Коллекция показывается агрегированно (число сущностей, статистика индексов, дорогие запросы и широковещательные реакции) с drill-down по id; инстанс-скоупы не регистрируются как обычные скоупы — иначе тысяча скоупов за кадр кладёт devtools.

### 10.4 Место пакета

Сабпас **`@virentia/core/models`**: одна версия с ядром, атомарная эволюция внутренностей (цепочки скоупов, маршрутизация, пулинг, инспектор); отдельная точка входа не стоит байт тем, кто не импортирует. Вместе с этим `owner` уходит в `@virentia/core/internal` — публичными остаются `onCleanup` и `dispose` на экземплярах.

`@virentia/mutable` переезжает тем же приёмом в **`@virentia/core/mutable`** (зависимостей кроме core у него нет, перенос механический); пакет `@virentia/mutable` удаляется: финальная версия — тонкий реэкспорт сабпаса с deprecation-нотисом, затем архив.
